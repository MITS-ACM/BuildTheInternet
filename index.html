Build The Internet

A hands-on technical challenge to build and connect a mini internet system through contract-driven microservices.

Excel Lab, MITS Kochi 2:00 PM — 6:00 PM

Rules of engagement

  • Microservices only. The system must be four distinct services. Monolithic architectures will not be evaluated.
  • Dynamic discovery. Services must use the DNS service to find each other. Direct communication bypassing DNS is prohibited.
  • No hardcoded IPs. Every address must be injected at runtime via user input or environment variables.
  • Visual client. The client must be a web application featuring a real-time visual progress indicator of all network hops.
  • Isolated development. Each team member takes ownership of exactly one microservice. Collaboration on a single codebase occurs only during final integration.
  • Strict contracts. Provided API endpoints and schemas cannot be modified or removed. Extending with new endpoints is permitted.

System contracts

acm-dns
Dynamic service discovery registry.
GET
/lookup?domain={name} Resolves a domain name to its current destination IP address.
POST
/register Body: { "domain": "auth-service" }
acm-db
Low-level user storage.
POST
/db/users Body: { "username": "alice", "password_hash": "..." }
GET
/db/users/{username} Retrieves a stored user record.
acm-server
Authentication and session management.
POST
/register Body: { "username": "alice", "password": "..." }
POST
/login Body: { "username": "alice", "password": "..." }
GET
/whoami Inspects the session cookie to return active user details.
acm-app
The web client gateway.

Expected execution flow:

  1. Accept DNS Server IP from user input.
  2. Query DNS for the auth server address.
  3. Attempt Login (If fail: Register, then Retry Login).
  4. Extract and persist the session_id cookie.
  5. Verify Session via the /whoami endpoint.
