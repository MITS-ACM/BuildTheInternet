The system contracts

Four clear roles. One shared contract.

Each teammate takes ownership of a different microservice. Use the provided OpenAPI 3.0 YAML specifications as the source of truth: you can extend an API, but you cannot alter or remove its required contract.

acm-dns

Dynamic service discovery

Acts as the registry for the system. Services register their names, and clients or other services look up the current address when they need to connect.

GET/lookup?domain={name}
POST/register

acm-db

User credential storage

Stores user records for the authentication service. Save password hashes rather than plaintext passwords, and return stored user details when requested.

POST/db/users
GET/db/users/{username}

acm-server

Authentication and sessions

Handles registration and login, hashes passwords, coordinates with the database, and uses cookies to maintain an authenticated session.

POST/register
POST/login
GET/whoami

acm-app

Interactive web client

Connects the user to the authentication flow. It accepts a DNS server address, discovers the auth service, handles the registration fallback, preserves the session cookie, and verifies the session. Visualize each hop and background event as it happens.

Keep the services independent

The four services must remain separate. Every service-to-service connection must be discovered through acm-dns, and addresses must be supplied dynamically through user input or environment variables.

Contract examples

DNS registration identifies a domain. Database writes include a username and password hash. Auth requests accept a username and password. Refer to the provided OpenAPI YAML for complete schemas and responses.
